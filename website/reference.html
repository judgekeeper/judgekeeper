judgekeeper reference

Every command, flag, exit code, file and format. The README has the short version.

Check your LLM-as-a-judge in 5 steps: Find. Mark. Measure. Fix. Re-check. judgekeeper does Find, Mark and Measure; judgekeeper mark marks more; judgekeeper fix shows where your judge goes wrong and tests a better rule; judgekeeper check re-checks your LLM-as-a-judge after a change. Run them in your own terminal: each run ends with one Next: line that says what you do. judgekeeper --help lists the commands, and judgekeeper <command> --help each command's flags.

judgekeeper: find, mark, measure

judgekeeper [PATH] [--tool NAME] [--metric NAME] [--experiment NAME_OR_ID]
            [--tracking-uri URI] [--pass-if RULE] [--label-map MAP] [--judge-model NAME]
            [--fields LIST] [--yes] [--port PORT] [--no-browser] [--new | --wait | --stop]
            [--version] [--debug]

Each run does the next step:

A new eval run does not start over: the answers you are marking are kept in .judgekeeper/pool.jsonl, so marking goes on with them. When the newest results hold answers you haven't seen and your judge is the same, they join your marking as a new batch: "Your newest results have 15 answers you haven't seen. They're added for marking." When your judge changed since your marks, it says what changed, and once there are enough marks its Next: line is judgekeeper check. A judge whose results hold no rule (a CSV or JSONL table) changes only in its grades: when its grades on your marked answers differ in the newest results, it says "Your judge's grades changed on 7 of your marked answers." and its Next: line is judgekeeper check.

Your project folder. Every command keeps .judgekeeper/ in your project folder and finds it the same way: from the folder it runs in (or the PATH folder), the nearest folder up whose .judgekeeper/ holds your marks, without leaving the project (a folder with pyproject.toml, package.json, .git, setup.py or judgekeeper.toml). So judgekeeper, mark, --stop, check and fix find the same marks and page from the project and from a folder inside it. A results file or MLflow store given as PATH never moves it: the file is read where it is, .judgekeeper/ stays in the project you run from, and later runs without a PATH read that file again. When your results file is gone, your marks stay in .judgekeeper/, and it says so; they come back when the file is back. Run from a folder that holds several projects, it says which project the results are from and names the others with the command that checks them. Run from a project, it never reads the results of a project inside it (a folder with its own project file or .judgekeeper/): it names that project and says to run judgekeeper there. Run from that inner project for the first time, it says when the project above holds marks for its results.

Options may come before the command: judgekeeper --no-browser mark is judgekeeper mark --no-browser. A flag a command does not have prints that command's usage and points to judgekeeper <command> --help.

judgekeeper can read results from promptfoo, DeepEval, Inspect AI, MLflow, or a CSV or JSONL file with input, output and verdict columns (What it reads).

The marking page shows one answer at a time, with your judge's grade hidden; you mark it Pass or Fail, the way you want your judge to decide (keys ← Fail and → Pass, S to skip, Z to undo). Your judge's rule is not shown. "See your result" appears once there are enough marks of each kind. With every answer marked, the page closes once you open your result. The page runs on 127.0.0.1 with a random token in its link. The page accepts marks only from itself, so another website can't send marks. A program on your computer could, the same way it could edit your files. When the program named in BROWSER opens the page, or its link is printed with no terminal, each mark is stamped so, and the result says how many marks came that way. Every click is saved at once. On your result page, say why on the answers you and your judge disagree on (never on marks kept aside): tap reasons, a part of your rule or your own reasons (typed once in "Other…", then a button), and select words in the answer to mark them; fix puts your reasons next to its mistakes, counts them in its clues and suggests rule lines in .judgekeeper/fix/suggestions.md.

Exit codes: 0 the next step is done, 3 you are needed (the Next: line says what to do), 2 a usage error, 130 Ctrl-C.

mark: mark more answers

judgekeeper mark [PATH] [--tool NAME] [--metric NAME] [--experiment NAME_OR_ID]
                 [--tracking-uri URI] [--pass-if RULE] [--label-map MAP] [--judge-model NAME]
                 [--fields LIST] [--yes] [--port PORT] [--no-browser] [--new | --wait | --stop]

Opens the marking page again, to mark more answers; more marks make your numbers more precise. Run judgekeeper afterwards to see your updated result. When every answer is marked, it says so. If you and your judge disagree on answers you can see, it opens your result page (the link printed with --no-browser ends in /result), with its reason buttons: say why on each, and fix uses your reasons. Else it opens no page: run your eval on more questions, then judgekeeper mark again, and the new answers join the ones you marked as a new batch, offered first on the page; with too few of one kind for a result it says it as judgekeeper does, and the marking page's last card says the same. When two runs open the page of one project at the same time, the second says "judgekeeper is already opening the marking page for this folder", waits, then opens it and prints its link. It takes the same flags as judgekeeper, without --version and --debug.

fix: see where your judge goes wrong and test a better rule

judgekeeper fix [PATH] [--yes] [--new]

It needs a result (enough marks of each kind). Each run does the next step:

What is thereWhat judgekeeper fix does
No new rule in .judgekeeper/fix/rule.txtKeeps some of your marks aside (about 30% of each group: your judge's passes and fails, where you agree with it and where not; at least 5 marked Pass and 5 marked Fail). On the other marks: the clues, under "Clues:" (your reasons from the result page, counted; too easy or too strict, mistakes near the pass mark, long answers, words found in many of its mistakes), and .judgekeeper/fix/mistakes.md: what to do in one line, the same clues, your judge's rule, then each mistake with your mark, its grade, the question, the answer, your reason and its own reason, fenced as data. You can hand the file to a coding agent. Where your judge's rule is written (file and line), looked for only in your project's config and code, never in a .txt file, a log or a saved copy of judgekeeper's output; when it can't tell, it says so and names where your eval tool keeps the rule
A judge with a score and a pass markAlso tests the pass mark that fits the other marks best on the marks kept aside, with the saved scores, with no AI call. Shown when it is better or safe to try
A rule in rule.txt already tested on these marks kept asideShows that test's saved result ("You tested this rule before") and its next step; your judge is not asked again

[y/N] (without a terminal, --yes). Then it asks your judge about the answers kept aside, once with the old rule and once with the new one, in the same run, and gives the result. A judge whose rule judgekeeper can't swap in (a table, record(), your own format, or a rule per test)Says "judgekeeper can't re-run this kind of judge itself.", then: change its rule where your eval keeps it, run your eval, then run judgekeeper check. It says the same on every run and never reads rule.txt; the report's Fix it says the same. Unless its grades follow a pass mark, it keeps no marks aside and lists every mistake. After a check found its new grades worse, the mistakes are the new grades'
FlagWhat it does
PATHYour project folder (default: this folder)
--yesWithout a terminal: go ahead and test the new rule (it makes AI calls, paid with your own key)
--newKeep a new set of your marks aside to test rules on

The marks kept aside are never shown: nothing prints them or writes them anywhere but .judgekeeper/fix/split.json, so a new rule is never written from them. They stay the same until --new. Marks of a new batch are kept aside the same way, within each of its groups, once that batch counts toward the result.

The result, from the marks kept aside: fixed (the old rule was wrong, the new one right) and broke (the other way round).

ResultWhen
Better / WorseThe exact two-sided sign test on fixed against broke, at 5%
Safe to tryElse, a non-inferiority test (Tango's score test for paired proportions, one-sided 2.5%) rules out the new rule being more than 10 points worse
Can't tell yetElse; it says whether it leans toward better, looks the same, or leans toward worse (keep the old rule). Only a split past the sign test is called worse

Each extra test on the same marks kept aside is stricter (the levels divided by the number of tests), so trying rule after rule can't turn a coincidence into "better". Over all tries on one set, a wrong "safe to try" stays under about 1 in 20. After a "can't tell yet" that leans toward better, it asks once for a few more marks (7 when about 10 are kept aside, 9 when about 15): they join the marks kept aside and the same rule is tested again. After 3 rules, 10 new marks become a new set of marks kept aside; when the 3rd rule leans toward better, it asks for those 10 at once (no top-up), and tests that rule again on the new set. A new rule written in rule.txt while marks are awaited is said to be waiting for them.

Your judge's rule is swapped in by judgekeeper when it asks: promptfoo's assertion value, a DeepEval GEval's evaluation steps (or criteria), an Inspect scorer's instructions, an MLflow make_judge's instructions or a Guidelines text. A judge whose rule can't be swapped (a table, your own code, a registered or built-in MLflow judge) is told to change the rule itself, run its eval and judgekeeper check. judgekeeper never changes your files. Each test is saved: the rule in .judgekeeper/rules/<hash>.txt, and a line in history.jsonl (the rule's hash, the counts and the result; no answer text).

Exit codes: 0 the step is done, 3 you are needed (more marks, a rule to change, or the question needs your answer), 2 a usage error.

judgekeeper check [PATH] [--yes]

FlagWhat it does
PATHYour project folder (default: this folder)
--yesWithout a terminal: go ahead and ask your judge (it makes AI calls, paid with your own key)

When something changed, it re-checks the new judge on your marks. First, with no AI call: answers you marked whose exact text is in your newest results already have the new judge's grade. For the rest it asks your own judge, through your own eval tool and with your own key: it says how many answers and AI calls that is, and asks Go ahead? [y/N] (Enter is No). Without a terminal it needs --yes, else it stops before any call (exit 3). When the key your judge needs isn't set, it names the key and where to set it (your shell, or .env when your eval tool reads it), never its value. It asks about each answer twice and compares the first grade; the second shows how often your judge changes its own grade, so a small difference can be told from that. Then, for the answers you passed and those you failed, how many of your marks the old and the new judge agreed with, how many went from right to wrong and how many from wrong to right, and a result from a range on that change: "Worse" (the whole range is a drop), "No drop bigger than 20 points" (its low end is above that), or "Not sure". It always says the worst drop the marks could hide. Each group is checked on its own. In about 1 check in 10 at most, coincidence alone flags a drop in one of the two groups; mark more answers before acting on a small one. The rates history.jsonl keeps are corrected for how the marks were picked, the same as the result's. Each check is a line in .judgekeeper/history.jsonl (no answer text). Marks you add after a check are re-checked by the next check ("You added 10 marks since your last check."). After a check that is not "Worse" or "Not sure", your marks test the new judge: the result, its "This result is about your judge as it was on…" line and fix's mistakes.md describe the judge in your newest results. After a "Worse", your marks keep testing the new judge against the old one: every check says it is worse until you go back to the old judge or change it again, and judgekeeper and the report give the same next step as check. A "Not sure" stays open the same way: the next check of the same judge says "Not sure" again, until you change the judge again or more marks are re-checked. Back on the judge your marks were made on, after a check of another one (worse or not), check and judgekeeper say "Your judge is back to the one you marked with (…). Your marks' result still holds.", with no AI call: your marks test that judge again, with the grades they were made on.

Exit codes: 0 no drop bigger than 20 points, not sure with a smaller drop, or nothing changed; 1 worse, or not sure with a drop bigger than 20 points; 3 you are needed (not enough marks, nothing could be re-checked, or the question needs your answer), 2 a usage error, or your judge was asked through another model than your new judge's (nothing is saved).

How the numbers are worked out

What it checks first, with no AI call. Before you mark anything, judgekeeper looks at the judge's own grades: no marks, no AI call, no key. It says what it found, one line each, each starting with "Checked:":

  • No real decision. The judge's call failed (DeepEval's error, or no score with success false; promptfoo's graderError, or in older files its grader-failure reasons such as "API error:"; Inspect AI's grader_failed, or a sample that errored before it was scored; MLflow's feedback.error), its reply could not be read (promptfoo's "Could not extract JSON" or "Error parsing output"; Inspect AI's "Grade not found in model output"), or there is no decision at all (a blank cell). These answers are left out, and it says what your eval tool counted them as: promptfoo and DeepEval count them as fails.
  • Checked nothing. A DeepEval metric whose judge returned nothing to check scores a full 1.0 and passes (its logs show an empty Verdicts: list). Left out too.
  • Passed an empty answer. The app's answer is empty and the judge passed it. Kept: it is a real decision, and a good one for you to mark.
  • The same grade for every answer. The judge passed (or failed) all of them.
  • The reason says the opposite. The judge's reason starts with PASS, PASSED, FAIL or FAILED, or its last verdict:, grade:, result:, decision:, final verdict: or final answer: says pass, fail, correct or incorrect (or Inspect AI's GRADE: C or GRADE: I), and either of them is the other grade. No other words count, so "does not fail" or "partially correct" are never flagged. Skipped for a judge that grades with a score and a pass mark.

None of these stops it. When nothing is found it says "Checked: your judge gave every answer a clear Pass or Fail." The answers found are listed in .judgekeeper/judge-check.csv and judge-check.json.

Which answers you mark. From the newest results it takes every answer with a clear Pass or Fail, counted once (the same input and output; the newest file wins). With too few answers for a first result, it says so and says how to make more with your own eval tool. The page shows the answers in blocks of 10 in a seeded order, 5 from the judge's passes and 5 from its fails, so you see both kinds early. Your marks decide Pass and Fail; the judge's grades only decide how answers are picked.

New answers join as batches. The answers you first mark are batch 1. When judgekeeper or judgekeeper mark finds answers in your newest results that are not in your marking (by their exact question and answer text), each with a clear Pass or Fail from the same judge, they join as the next batch. A batch never removes or replaces an answer: an answer whose text changed is a new answer. When your judge changed, nothing joins: that is judgekeeper check. The page offers the newest batch first, in blocks of 10 with 5 of the judge's passes and 5 of its fails, then any older batch's answers not marked yet. The numbers are corrected per batch: each batch's passes and fails are groups of their own, weighted by their size, and the ranges are drawn group by group. With one batch, every number is the same as before batches. A batch after the first counts toward the result once each of its groups has at least 5 marks, or all its answers marked. Until then it is left out, and the result says so: "This result is on 2 of 3 batches (140 answers). 15 newer answers need a few marks first." report.html says the same, and history.jsonl keeps which batches each result is on. check and fix use the marks of the batches that count, weighted the same way. The coverage check runs batches too: on two and three batches of different sizes, with judges whose accuracy differs between batches and 10 to 40 marks per group, the ranges held the true value at least 93.2 times in 100 in every case and 95.8 on average (docs/examples/coverage/coverage.md, Batches). --new still starts over, as a last resort.

The result. TPR (of the answers you passed, how many your judge passed), TNR (of the answers you failed, how many it failed) and the real pass rate are corrected for showing far more of the judge's fails than the pool holds: worked out per group and weighted by the group's size. Their ranges come from Jeffreys draws: each group's share of answers you marked Pass gets the distribution Beta(passes + 0.5, marked − passes + 0.5); 20,000 pairs of draws, with a fixed seed so the same marks always give the same ranges, go through the same formulas, and a range is the middle 96% of what comes out (widened, if needed, to hold the number itself). The 96% was chosen by a coverage check, not assumed: docs/examples/coverage/coverage.md simulates thousands of checks for judges that pass 50%, 70% and 90% of answers, agree weakly to strongly, and 10 to 40 labels per group. At 96% the ranges held the true value at least 93.6 times in 100 in every case and 96.2 on average; 95% fell to 91.6 in one case. The ranges before (Wilson at 97.5% per group, joined at the corners) held it 99.1 times in 100 on average: too cautious, so they were wider than needed; the ranges now are 27.1% narrower on average. On real data too: on 5 real judges from 3 public datasets, with 25 + 25 labels, the TPR and TNR ranges held the value worked out from all of the dataset's human labels in 96.0 checks in 100 on average (lowest 94.6, highest 98.4), over 1,000 checks per judge: docs/examples/real-data-check/report.md. Kappa is Cohen's kappa on the weighted table (your real mix of answers), with its range from the same draws. Kappa moves with how many answers pass, so it is in the report's More details only and never decides the result.

What it says. The terminal and the report say the same, in the same order. First one result line, from the ranges, never a number alone: "Your judge is good enough to use." when the low end of both ranges is at least 80%; "Your judge needs work." when a range stays below 80%; else "Too early to tell. Mark more answers to get a result." Then how many answers you and your judge disagreed on (or "agreed on all N answers"), and plain counts: of the answers you passed, how many your judge passed and failed, and the same for those you failed. Then "How often your judge agrees with you (estimates)": "When you say Pass, it also says Pass: about N% (between A% and B%)" and the same for Fail. A side whose range is more than 40 points wide says "too early to tell". While the result is "Too early to tell", the terminal shows the counts only, no estimates; the report keeps its More details once neither range is that wide. Both end with the same next step: judgekeeper mark while it is too early to tell, judgekeeper fix when your judge needs work, nothing when it is good enough. While it is too early to tell, fix is never the next step. With every answer marked there is nothing left to mark: the result line drops "Mark more answers to get a result.", neither offers the page, and both say "You've marked every answer: 29 Pass, 26 Fail. That's still too few to tell." (or, with under 15 of one kind, what a result needs), then to run your eval on more questions and judgekeeper mark: the new answers join the ones you marked. fix and check then give that same next step wherever they would ask for more marks. The report also lists the answers where you and your judge disagree, in two groups, with your judge's own reason; marks kept aside for judgekeeper fix are counted, not shown. Under the disagreements, the terminal and the report say once: "To say why on these, run judgekeeper mark." (not after a check found your new judge worse). Kappa is under its More details. judgekeeper fix prints where your judge goes wrong: which side most of its mistakes are on, and words found in many of them.

What it reads

It looks only inside the folder, to a depth of four folders, skipping .git, node_modules, virtual environments and hidden folders (except .deepeval, and .judgekeeper/records/, where judgekeeper.record() writes). It stops after 5,000 files or 2 seconds and, when it found nothing, says so. It does not follow symbolic links, and results files over 200 MB are listed, not read. A results file with no LLM-as-a-judge in it (checks written in code, DeepEval metrics with no model, promptfoo's table output) is left out with one line; an empty file or one it can't open is named. When it finds nothing, it says how deep it looked, names the results-like files it left out (further down, a link, in the folder above, or not saved as UTF-8, such as Excel's "Unicode Text") with the command that reads one, and, run from a subfolder of a project (a folder above with pyproject.toml, package.json or .git), reads the project folder instead. A big file says how far reading has got on stderr every few seconds after the first two. From an MLflow experiment it reads the newest 30,000 traces and says so when there are more (reading each trace takes about a millisecond). The marking page gets the answers up to the furthest one marked and the next 100, never the whole pool. Your eval tool's files are only read, never changed.

Tested with promptfoo 0.120 to 0.124. Your promptfoo config does not change. To ask your judge again (fix, or a check that makes AI calls), judgekeeper runs the promptfoo version your results were made with: the project's or the one on your PATH, else npx promptfoo@<version>, whose download is part of the same Go ahead? [y/N] question; without npx, it names the install command, such as npm install promptfoo@0.124.0. When promptfoo's results are only in its own database, judgekeeper prints the promptfoo export eval commands that save them to a file (they run no test and cost nothing).

A judge whose assertion value differs per test shows as "Judge rule: differs per test (12 rules)" with the first one, and factuality as "compared with each test's reference answer" (its value is that answer, not a rule). --metric names the judge: an assertion's metric: if it has one, otherwise its type (llm-rubric, g-eval, factuality, model-graded-closedqa, model-graded-factuality, answer-relevance, context-faithfulness, context-recall, context-relevance, conversation-relevance, search-rubric). With only one such judge in the file you can leave it out; with several, judgekeeper asks which. Other assertions (contains, javascript, ...) are code checks: they are ignored, with a note. Item ids: each test's description when every test has a unique one, otherwise a hash of the test's vars (not its output, which can differ between repeats). With several prompts, ids get #prompt<n>.

Traps.

  • A human rating overrides the row's success and pass. judgekeeper never reads the judge's grade from them: it reads the model-graded component itself.
  • --repeat rows carry no repeat index. promptfoo removes __repeatIndex before saving and gives every repeat its own testIdx (with the same promptIdx and identical vars), so testIdx does not identify a test. judgekeeper groups rows by item id and promptIdx and numbers the repeats in the order they appear in the file. If your outputs differ between repeats (no provider cache), each item keeps the output of its first repeat.
  • The default grader is not recorded. With no provider on the assertion, the test's options, defaultTest.options or defaultTest.provider, promptfoo grades with its built-in default model and the results file does not say which. Those grades get an unknown model, and Find says how many of your judge's grades came from promptfoo's default grader. Set the grader explicitly (below); the temperature is recorded only when the provider config carries it.
  • A grader set with --grader is saved without its provider, only its model name. judgekeeper records that model, leaves the provider unknown and says so.
  • The prompt hash is the assertion's value (the rubric) plus rubricPrompt when set. For llm-rubric, promptfoo also saves the exact text it sent the grader (renderedGradingPrompt): with the answer and the test's vars put back as placeholders, that is the grading template, and when it is the same on every row its hash is the prompt hash, so a change in promptfoo's own grading prompt shows too. A different rubric per test gives a different hash per answer.
  • Cached grades. A grade promptfoo replayed from its cache (cachedResponse) may be an old reply; judgekeeper says how many there are.

DeepEval

export DEEPEVAL_RESULTS_FOLDER=deepeval-results
deepeval test run test_judge.py
judgekeeper --metric "Correctness [GEval]"

Tested with DeepEval 3.9.9 to 4.2.8. Your test code does not change. DeepEval has no --output-file flag. It writes .deepeval/.latest_run_full.json, overwritten by every run, and one test_run_<YYYYMMDD_HHMMSS>.json per run in a results folder when you set one (DEEPEVAL_RESULTS_FOLDER, or in Python evaluate(..., display_config=DisplayConfig(results_folder="deepeval-results"))). Results are saved only when tests run through deepeval test run or evaluate(): calling a metric's measure() directly saves nothing. When both .deepeval/.latest_run_full.json and test_run_*.json files are there and hold different runs, the newest run by time is read, and one line names the other with both dates. A run with no test cases says "The run has no test cases." DeepEval's results don't hold its version: judgekeeper reads it from your project's pin (uv.lock, poetry.lock, pyproject.toml or requirements*.txt), and without one it suggests pinning the version you have installed. --metric is the metric's name as it appears in metricsData (GEval metrics are named "<name> [GEval]"). The grade is the metric's success; with --pass-if "score>=0.7" judgekeeper applies that rule to score instead. A GEval judge built with evaluation steps and no criteria is shown by its steps.

Traps.

  • Default test case names are positional. Without LLMTestCase(name=...), DeepEval names cases test_case_0, test_case_1, ... by order, which is not an id. judgekeeper then makes each id from the case's input and actual_output and warns. Those ids only line up across runs if the outputs are the same in every run; name your test cases for stable ids.
  • The rubric lives in verboseLogs. For GEval, the prompt hash covers the Criteria:, Evaluation Steps: and Rubric: parts of verboseLogs, not the per-item Score: line. Metrics without those parts get an unknown prompt hash.
  • Temperature is not written. The judge's model comes from evaluationModel; DeepEval does not store the temperature, so it is recorded as unknown. The provider comes from the suffix DeepEval adds to the model's name (claude-sonnet-4-6 (Anthropic), my-deployment (Azure), gemini-... (Gemini)); a bare name is OpenAI, since DeepEval builds an OpenAI model for any plain string. To ask a judge whose name has a provider's suffix again, judgekeeper builds that provider's model class with the saved name, never DeepEval's default model first; when DeepEval's own error names a setup command of its own (deepeval set-…), the Next: line gives that command as DeepEval wrote it.
  • An empty answer. DeepEval refuses an empty answer and saves an error instead, so it counts as no real decision.
  • DEEPEVAL_LOCAL_STORE=sqlite writes deepeval.db and no JSON. Leave it unset.

Inspect AI

inspect eval task.py
judgekeeper --metric model_graded_qa

Tested with Inspect AI 0.3.242 to 0.3.278. Your task does not change. Logs land in ./logs (or INSPECT_LOG_DIR). .json logs are read directly. .eval logs (Inspect's default, a zip archive) need the optional extra, installed in your project's environment: pip install "judgekeeper[inspect]". Without it, convert first (inspect log dump logs/x.eval > log.json), or write JSON logs with --log-format json; when the newest log is a .eval log, it says so, with the install line, before it reads an older .json one. To read one log, give its path: judgekeeper logs/log.json. Logs in more than one folder (two evals, each with its own logs/) are never read as one: it lists the folders and asks which, and judgekeeper.toml keeps the answer after a yes. --metric is the scorer's name, the key under samples[].scores (model_graded_qa, model_graded_fact, your @scorer name). Item ids are samples[].id; runs are samples[].epoch.

Traps.

  • Score values. C reads as pass and I as fail. P (partial credit) has no default: map it with --label-map P=fail (or P=pass), otherwise judgekeeper stops and lists the values it cannot read. Numeric values need --pass-if, e.g. --pass-if "score>=0.5".
  • Several values at once. A scorer whose value is a dict (rubric and checklist graders report this way, e.g. {"accuracy": "C", "tone": "I"}) is read as one judge per key, named <scorer>.<key> (rubric.tone); choose one with --metric.
  • Code scorers. match, includes, exact, pattern, f1 and answer check text in code, not with a model: they are not judges and are left out.
  • A sample that failed before scoring (the app or solver raised, so samples[].error is set and no score was saved) is no judge's decision: "2 answers have no score: the run failed before scoring." It is left out, never counted as a failed judge call.
  • Agent runs. Each sample's messages are kept as the records' trajectory (OpenAI-style steps), so two runs that end in the same answer by different steps stay two answers.
  • Fingerprint. The grader's model and temperature come from eval.model_roles.grader when the task uses the grader role; otherwise from the scorer's model option, with temperature unknown. The prompt hash covers the scorer's template and instructions options from eval.scorers[]; one left unset stands for Inspect's default for that scorer. The rendered prompt in score.metadata.grading is never hashed: it holds each sample's text. If you upgrade Inspect and its default template changes, the hash does not; set template explicitly to track it.
  • --no-log-samples logs have no samples and cannot be read.

MLflow

pip install "judgekeeper[mlflow]"
judgekeeper --experiment my-app-eval --metric correctness

Tested with MLflow 3.10 or newer: judgekeeper[mlflow] allows MLflow 3.1, but 3.10 is the oldest tested. Install the extra in your project's environment. judgekeeper reads the judge's assessments MLflow already stores on your traces, from the local store in your project folder: mlflow.db (through a temporary copy, never opened itself) or an mlruns/ folder (--tracking-uri picks one when there are both; at a terminal it asks). A local mlruns folder needs MLflow's folder-store setting from MLflow 3.16 on: judgekeeper switches it on (MLFLOW_ALLOW_FILE_STORE=true) for its own read only, and leaves your own value alone when you set one. --experiment takes a name or an id. --metric is the assessment name (your scorer's name). An LLM judge's assessment has source.source_type LLM_JUDGE and source.source_id set to the model (openai:/gpt-4.1-mini).

Traps.

  • Trace ids change every run. evaluate with a predict_fn logs new traces each time, so a trace id is not an item id. judgekeeper makes the id from the trace's request input (a hash), so the same dataset row maps to the same item in every run. Two rows with the same input are one item.
  • Which run. A judge assessment's run is its mlflow.assessment.sourceRunId metadata, which evaluate sets. Assessments logged outside evaluate have none and form one extra run, listed last, with a note.
  • Prompt and temperature. The fingerprint has the model from source.source_id (the provider is the part before :/) and, for registered scorers, scorerName@scorerVersion as the rubric version. A make_judge (MLflow 3.14 and later) saves its instructions with each assessment: they are the judge's rule, hashed into the prompt hash, so a changed rule is a new judge. Other judges' prompts are not saved with their assessments, so for them the prompt hash is unknown. Temperature is unknown.
  • Errors. A Feedback with an error (a judge that timed out) is an error grade, with the error code and message as its reason.
  • CODE assessments (a scorer that returns a bare bool or number) are not a judge and are ignored, with a note. Expectations (ground truth) are not grades and are not read.
  • Span-level assessments. An assessment logged on one span inside a trace (span_id) judges a step, not the answer. Only trace-level assessments (and those on the root span, where evaluate puts them) are read; span-level ones are left out with a note, unless --metric names a judge that is only on spans.
  • A copied mlruns/ folder. A folder store saves where each trace's files are as a full path. Copied or cloned to another computer, MLflow looks for them at the old path and drops every trace it cannot find. judgekeeper reads them from the store's own folder instead, and says how many answers it left out when their files are not there either.
  • MLflow's own problems, not judgekeeper's. mlflow.genai.evaluate on an mlflow.db store can drop traces when it runs out of database connections, while still saying the evaluation completed (fewer parallel workers, MLFLOW_GENAI_EVAL_MAX_WORKERS=4, avoids it); and an experiment made in mlflow.db keeps its artifacts in ./mlruns/ by default (give the experiment its own artifact_location). judgekeeper only counts the traces that were saved.

A CSV or JSONL file

A CSV, TSV or JSONL file with input, output and verdict columns (judge_verdict or judge work as the grade column too); a model or judge_model column names the judge's model, and id and reason are read when they are there. With --pass-if, a score column next to the verdict column is read in its place, and it says so in one line. The id column is each answer's id when every row has one and none repeats; otherwise judgekeeper makes its own and says so once. One file per judge or criterion. It prints the columns it read, the counts and the pass/fail split, so a wrong table shows. Rows where every cell is empty (a spreadsheet's last rows) are skipped. In a file separated by ; (Excel where the comma is the decimal mark), a score like 0,42 is the number 0.42. A title row above the header is named ("Row 2 looks like the header. Delete row 1 and run again."), and an Excel file (.xlsx) is not read: save it as CSV UTF-8. When the folder holds other result tables, it names up to three with the command that checks each. Give its path when it is deeper than two folders: judgekeeper results/judge.csv.

Results in a format of its own. When it finds no eval tool's results but a recent JSON, JSONL or CSV file (changed in the last 90 days, at most four folders deep) that holds, at any depth, a score-like key (score, scores, verdict, pass, passed, success, label) next to an input-like and an output-like key, or when you give it such a file, it shows the file's paths (never their values) and how it would read them: what one answer is, the input, the answer, the score, the reason, the id and the judge's model. It asks whether that is right, and then only what the file cannot tell (which of several judges, the pass mark when the scores are not between 0 and 1, whether to leave out scores made by a rule). --pass-if gives the pass mark with any operator (score>4, score<=2, score==5), and the box shows the pass mark that is used. A blank or NaN score, or one that is error, N/A or null, is no decision and is counted in the "no real decision" line. A part is the judge's grade only when its name says so (score, verdict, grade, label and the like, or a part inside a judge object) and most of its values are grades: pass or fail, true or false, yes or no, correct or incorrect, or numbers from 0 to 100. Ids, free text and a judge's settings (its pass mark, its criteria's text, a run id) never are. A reading it is not sure of (a part told by its values alone, or one answer from a file that holds a list of many) is never accepted by --yes: run it in a terminal to check it. With your yes it saves how to read the file in a [start] table of judgekeeper.toml, which it reads first next time. When the file cannot be read this way, it says so: turn it into a CSV with the columns id, input, output, verdict (pass or fail) and reason, one CSV per judge, and run judgekeeper PATH with PATH the path of the CSV; or save your judge's grades with judgekeeper.record().

judgekeeper.record()

When your judge runs in your own code, one judgekeeper.record() line saves each grade in .judgekeeper/records/ (below). judgekeeper reads every file written by the newest file's judge (one eval run can be many processes, so many files; a newer file wins for a repeated answer). Several judge names: it asks which, --metric answers. A last line cut short is left out; a file it cannot read is left out, and it says so.

How grades are read

One normaliser reads every grade from your judge (with --pass-if and --label-map) and every mark. It turns a raw judge output into pass/fail or error, plus a reason:

  • a bool: True is pass;
  • a string, case-insensitively, through the label map. Defaults: pass/fail, true/false, yes/no, correct/incorrect, right/wrong, 1/0, and a leading PASS or FAIL token (PASS: looks right); error, N/A, null, none and nan are no decision. --label-map "good=pass,bad=fail,maybe=error" adds entries (=error for no decision);
  • a number, through a required --pass-if rule: score>=0.5, >, <=, <, ==. The name is free text, except that for a dict it names the key to read (relevance>=3). Integers 1/0 follow the label map when no rule is given;
  • a (grade, reason) tuple or two-element list;
  • a dict with the grade under verdict, pass, passed, label or score (first found) and the reason under reason, rationale, explanation or comment.

A value that looks like a grade but is not in the map (good), or a number with no rule, is a usage error that lists every such value seen. judgekeeper never guesses. A judge that raised, returned nothing (None, an empty string, NaN, or a word for none such as N/A) or returned something unreadable (a dict with no grade key, a list of three) is recorded as error, never as fail: errors are left out of every agreement number.

record(): save your own judge's verdicts with one line

When your judge runs in your own code and saves nothing judgekeeper reads, add one line right after it gives each grade, in your eval code:

import judgekeeper
judgekeeper.record(input=question, output=answer, score=0.82, pass_mark=0.5,
                   reason=reason, judge="claude-opus-5", rule=criteria, name="Safe wording")

Then run your eval once and judgekeeper: it finds the records. Install judgekeeper inside your project's environment (pip install judgekeeper) for the import.

Each call writes one line in the records format (version 2, annotator_kind LLM) to .judgekeeper/records/<name>-<date>-<process id>.jsonl under your project root: the nearest folder upward from where your eval runs that has judgekeeper.toml, pyproject.toml, setup.py, .git or a requirements*.txt (never your home folder), else the current folder. One file per process, so evals that run in several processes never write to the same file. judgekeeper reads the files of the same judge together, as one set: an answer saved in more than one file (a second run, or the same day again) counts once, with the grade from the newest file. Each line is written whole and the file closed at once; a lock keeps threads' lines apart.

A score or pass mark may be any real number: an int or float, a numpy number, a Decimal, or text such as "0.8". It never breaks your program: any error inside it is caught and it returns nothing. The first grade it can't save is logged to the judgekeeper logger at once; any more are counted, and the count is logged when your program ends. It uses only Python's standard library, and import judgekeeper loads nothing else until you call it. The file holds your inputs and outputs: use it in your eval code, not in code that serves real users. JUDGEKEEPER_RECORD=0 (or false, off, no) turns it off.

Without the import, or in another language. Copy one of these into your eval code. The Python function, jk_record, takes the same arguments as judgekeeper.record() and writes the same lines, with nothing to install; the TypeScript one does the same for Node.js (jkRecord(input, output, { score, pass_mark, ... }), the same names in its options). Run them from your project folder: unlike record(), they do not look upward for the project root.

# Saves each judge grade for judgekeeper; run it from your project folder. Standard library only.
# It takes the arguments of judgekeeper.record() and writes the same line.
import json, os, re, time
def jk_record(input=None, output=None, *, verdict=None, score=None, pass_mark=None,
              reason=None, judge=None, rule=None, name=None, temperature=None, id=None,
              metadata=None):
    try:
        name, now = "judge" if name is None else str(name), time.gmtime()
        meta = dict(metadata or {})
        if pass_mark is not None:
            meta.setdefault("pass_mark", pass_mark)
        label = verdict
        if isinstance(verdict, bool):
            label = "pass" if verdict else "fail"
        elif isinstance(verdict, str) and verdict.strip().lower() in ("pass", "fail"):
            label = verdict.strip().lower()
        elif verdict is None and score is not None and pass_mark is not None:
            label = "pass" if score >= pass_mark else "fail"
        line = {"schema_version": 2, "target_id": None if id is None else str(id), "name": name,
                "annotator_kind": "LLM", "label": label, "score": score,
                "explanation": None if reason is None else str(reason), "run": None,
                "input": input, "output": output,
                "evaluator": {k: v for k, v in (("model", judge), ("temperature", temperature),
                                                ("rule", rule)) if v is not None},
                "created_at": time.strftime("%Y-%m-%dT%H:%M:%SZ", now)}
        if meta:
            line["metadata"] = meta
        folder = os.path.join(".judgekeeper", "records")
        os.makedirs(folder, exist_ok=True)
        file = re.sub(r"[^A-Za-z0-9._]+", "-", name).strip("-.")[:60] or "judge"
        file += f"-{time.strftime('%Y-%m-%d', now)}-{os.getpid()}.jsonl"
        with open(os.path.join(folder, file), "a", encoding="utf-8", newline="\n") as f:
            f.write(json.dumps(line, ensure_ascii=False, default=str) + "\n")
    except Exception:
        pass  # a record never stops your program
// Saves each judge grade for judgekeeper; run it from your project folder. Node.js only.
// It takes the arguments of judgekeeper.record() and writes the same line.
import { appendFileSync, mkdirSync } from "node:fs";
import { join } from "node:path";

type JkFields = { verdict?: unknown; score?: number; pass_mark?: number; reason?: string;
  judge?: string; rule?: string; name?: string; temperature?: number; id?: string | number;
  metadata?: Record<string, unknown> };

export function jkRecord(input: unknown, output: unknown, f: JkFields = {}): void {
  try {
    const name = f.name ?? "judge", now = new Date().toISOString();
    const meta: Record<string, unknown> = { ...(f.metadata ?? {}) };
    if (f.pass_mark != null && !("pass_mark" in meta)) meta.pass_mark = f.pass_mark;
    const said = typeof f.verdict === "string" ? f.verdict.trim().toLowerCase() : "";
    let label: unknown = f.verdict ?? null;
    if (typeof f.verdict === "boolean") label = f.verdict ? "pass" : "fail";
    else if (said === "pass" || said === "fail") label = said;
    else if (f.verdict == null && f.score != null && f.pass_mark != null)
      label = f.score >= f.pass_mark ? "pass" : "fail";
    const evaluator = Object.fromEntries(Object.entries(
      { model: f.judge, temperature: f.temperature, rule: f.rule }).filter(([, v]) => v != null));
    const line: Record<string, unknown> = { schema_version: 2,
      target_id: f.id == null ? null : String(f.id), name, annotator_kind: "LLM", label,
      score: f.score ?? null, explanation: f.reason == null ? null : String(f.reason), run: null,
      input, output, evaluator, created_at: now.slice(0, 19) + "Z" };
    if (Object.keys(meta).length) line.metadata = meta;
    const folder = join(".judgekeeper", "records");
    mkdirSync(folder, { recursive: true });
    const file = name.replace(/[^A-Za-z0-9._]+/g, "-").replace(/^[-.]+|[-.]+$/g, "")
      .slice(0, 60) || "judge";
    appendFileSync(join(folder, `${file}-${now.slice(0, 10)}-${process.pid}.jsonl`),
      JSON.stringify(line) + "\n");
  } catch { /* a record never stops your program */ }
}

Unknown judge fields

Every fingerprint field except created_at may be unknown: provider, model, snapshot, prompt hash, rubric version and temperature are null, and an unknown endpoint is the string "unknown" (because endpoint: null already means the provider's default endpoint). Files from earlier versions still load: a missing field reads as unknown, except a missing endpoint, which reads as the provider default.

The .judgekeeper/ folder

judgekeeper writes only inside .judgekeeper/ in your project. On macOS and Linux, only your user can read what it writes there: its files are 0600 and its folders 0700. Every string from a results file is scrubbed of credentials before it is written. It does not write through links: if .judgekeeper/, or anything in it, is a link (a symlink, as a cloned repository can hold), it stops and says which, before writing anything. Every file is written as a new file that replaces the old one. Your own .gitignore is never changed: the folder holds your answers' text, so commit it only if your data may live in your repository.

Your API keys

  • Your key is used only by your own eval tool, when it asks your judge. judgekeeper has no server: your eval tool's requests go from your machine straight to the provider. A key in promptfoo's config env: block counts, as it does in your own promptfoo runs: judgekeeper passes that block to promptfoo in its environment.
  • judgekeeper never prints a key or writes one to a file. Before any text reaches disk or your terminal, the value of ANTHROPIC_API_KEY, OPENAI_API_KEY, MLFLOW_TRACKING_PASSWORD and any variable ending in _API_KEY, _TOKEN or _SECRET (DATABRICKS_TOKEN, MLFLOW_TRACKING_TOKEN) is replaced with [REDACTED], as is anything shaped like a key: OpenAI and Anthropic (sk-ant-…, sk-…), AWS (AKIA…, ASIA…, and a 40-character secret after aws_secret_access_key or AWS_SECRET_ACCESS_KEY (then =, : or a space, with quotes or not) or on the same line as an AKIA… or ASIA… key; a 40-character string with neither clue is left as it is, since guessing would hide real text), GitHub (ghp_…, gho_…, ghs_…, ghu_…, github_pat_…), Google (AIza…), Slack (xoxb-…, xoxp-…), Bearer … and Basic …. So is the user:password@ part of a URL.
  • Finding, marking and the result make no AI call and need no key. Before any AI call, judgekeeper says how many calls it makes and asks first (Go ahead? [y/N], Enter is No). Without a terminal only --yes says yes.
  • Error text is scrubbed too. An unexpected error prints one line, never its own text (it can hold an answer's text), and exits 2; --debug adds where it went wrong (files, lines and the error's type, never the error's text), still scrubbed. The Next: line says to report it at github.com/judgekeeper/judgekeeper/issues with the lines above.
  • There is no flag that takes a key, and there never will be.
