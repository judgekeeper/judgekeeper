Check your judge, step by step

Six steps. Each one says what to do, what you will see, and how you know it worked. Your judge is the AI that grades the answers your app writes, in your evals.

You need

  • Python 3.11 or newer
  • A project whose judge has graded some answers, with promptfoo, DeepEval, Inspect AI, MLflow, a table or your own code

You will end with

  • How often your judge agrees with you, in two plain sentences
  • The answers where it disagrees with you
  • Everything saved in your project, on your computer
Using a coding assistant? Paste this prompt instead Claude Code, Cursor or Codex 
Help me check my LLM-as-a-judge with judgekeeper in this project:

1. Install judgekeeper inside this project's own Python environment, as a dev tool:
   `uv add --dev judgekeeper`, `poetry add --group dev judgekeeper`, or
   `pip install judgekeeper` with the project's virtual environment active. Never
   install it for the whole computer.
2. If `judgekeeper start` finds no results, run `judgekeeper setup` and show me its
   questions instead of answering them for me.
3. Run `judgekeeper start --yes --no-browser` and give me the link it prints. I will
   mark the answers myself: never mark them for me.
1

Install

judgekeeper is a tool for developers, like pytest. Install it inside your project, in the project's own Python environment, not on your computer as a whole.

Terminal, in your project folder

source .venv/bin/activate
pip install judgekeeper
judgekeeper --version

PowerShell, in your project folder

.venv\Scripts\activate
pip install judgekeeper
judgekeeper --version

What you will see

✓ judgekeeper 0.2.0 is ready
Next: run judgekeeper start

The package is judgekeeper on PyPI. Add it to your project's dev requirements, so everyone who works on the project gets it.

You're done when the first line ends in is ready.

Didn't work?
Not sure which Python you have
Run python3 --version (on Windows py --version, or python --version when Python is on the PATH). You need Python 3.11 or a higher number, such as Python 3.13.2. Command not found, or a lower number? Install Python from python.org/downloads and open a new terminal.
No .venv folder in your project (no such file or directory, or on Windows cannot find the path)
An environment (a virtual environment) is a folder in your project that holds its own Python and what the project needs. Make one with python3 -m venv .venv (on Windows py -m venv .venv), then run the activate line again. The start of the line then reads (.venv). If your project keeps its environment in another folder, such as venv, use that name.
Your project uses uv or Poetry
Add judgekeeper as a dev tool instead: uv add --dev judgekeeper or poetry add --group dev judgekeeper.
error: externally-managed-environment
Your project's environment is not switched on, so pip tried to install into the Python of your whole computer, which Homebrew, another program or the system protects. It is not about judgekeeper. Run the activate line, check that the line starts with (.venv), then install again.
pip: command not found (a Mac may say zsh: command not found: pip)
Outside an environment, a Mac names the command pip3. Switch on your project's environment: inside it, pip works.
'pip' is not recognized as an internal or external command (PowerShell: The term 'pip' is not recognized)
Inside your project's environment pip is always found, so the environment is not switched on: run the activate line again. Or use the environment's own Python, which always installs into your project: .venv\Scripts\python -m pip install judgekeeper
PowerShell refuses to run the activate line
Run Set-ExecutionPolicy -ExecutionPolicy RemoteSigned -Scope CurrentUser once and try again. In Command Prompt the line is .venv\Scripts\activate.bat.
The judgekeeper command is not found
With your project's environment switched on, run python -m judgekeeper --version. It does the same thing. Put python -m in front of every judgekeeper command, or with uv or Poetry put uv run or poetry run in front.
It also says judgekeeper is installed outside a project
Your project's environment was not switched on when you installed. Switch it on, install again, and check again.

Connect your results

judgekeeper reads what your judge already saved. Pick the line that fits you.

I use promptfoo, DeepEval, Inspect AI or MLflow

Nothing to do. judgekeeper start finds your results by itself. Go to step 3. (What it reads.)

My judge saves results in a file of its own

Run this once in your project folder. It looks inside the file, asks only what it can't tell, shows 3 answers as it will read them, then asks once before it changes any file. It never edits your code. (More on setup.)

judgekeeper setup
My judge is code I wrote, and it saves nothing

Add one line where your judge decides on each answer, in your eval code, then run your eval once. Or let your coding assistant add it: More on record() has the prompt.

judgekeeper.record(input=question, output=answer, score=0.82, pass_mark=0.5,
                   judge="claude-opus-5", rule=criteria)

You're done when your results fit one of the three lines above.

Start

One command. It finds your judge and its saved answers, and says what it found.

Terminal, in your project folder

judgekeeper start

What you will see, for a project with promptfoo results

Looking in /Users/me/support-bot ...

judgekeeper found your LLM-as-a-judge:

  Eval tool       promptfoo
  Results file    results.json (saved 3 Oct 2026, 14:12)
  What it checks  "is polite and correct"
  Judge model     openai:gpt-4.1-mini
  Its decisions   212 answers: 171 passed, 41 failed
  ✓ Your judge made a real decision on every answer.

Next: in your browser, mark each answer Pass or Fail.
This shows how often your judge agrees with you.
Open it now? [Y/n]

You're done when it names your judge and asks Open it now? Press Enter.

Didn't work?
No saved eval results found in your folder
Your eval tool has saved no results in this folder yet: run your eval once, then judgekeeper start again. If your judge saves its results its own way, go back to step 2.
judgekeeper setup says Three ways on:
It found no file it can read as your judge's results. Pick one of the three ways it lists: give it your file's path, add the record() line, or have your coding agent write a table (all three).
No promptfoo results file in this folder.
promptfoo kept your results in its own database. judgekeeper offers to run promptfoo export for you, which writes them to a file. It asks first.
It says judgekeeper needs at least 30 answers to show a result
Your judge graded fewer than 30 answers. It prints the command that makes more with your own eval, naming your config, test file or task: run it (it calls your models, so it costs money), then judgekeeper start again. Or mark the ones you have: the result shows wider ranges with fewer answers. A judge that failed only a few answers is not a reason to stop: your marks decide what should fail.
Saved results from more than one eval tool: or These results hold more than one judge:
It lists them and asks which one. Pick the judge you want to check.
4

Mark

A page opens in your browser. It runs on your own computer and shows one answer at a time: does it pass your judge's rule?

Press ← for Fail (this answer breaks your judge's rule) and → for Pass (it follows the rule), or drag the card. S skips an answer you can't tell from the text, and U undoes the last one. Every click is saved at once, so you can stop at any time and run judgekeeper start later to carry on.

What your judge decided stays hidden, so it can't sway you. The dots at the top are your marks so far: click one to go back to that answer. Half the answers are ones the judge passed and half it failed, so you see enough of both.

You're done when the page shows See your result. Marking more answers narrows the result's ranges.

5

Your result

Press See your result any time. It shows in the page and in the terminal, and it is saved as .judgekeeper/result.html, which opens without judgekeeper running.

The two sentences are the answer. Then one line says whether your judge agrees with you often enough to use as a gate: an automatic check that can stop a release. Green: often enough. Amber: look at where it disagrees first. Red: not often enough yet.

  • TPR: of the answers you marked Pass, the share the judge passed.
  • TNR: of the answers you marked Fail, the share the judge failed.
  • Kappa: how much the judge agrees with you beyond lucky guessing. 0 is no better than chance and 1 is perfect.

The bar under each number is the range it is probably in: narrower means more answers back it. The numbers are estimates from the answers you marked, not a promise about the next ones. The page showed you far more of the judge's fails than your results hold, so the numbers are corrected for that, and describe all of your app's answers.

You're done when you have read the two sentences. That is your answer.

6

Improve your judge

Run judgekeeper start again any time: it offers what fits next. Or go straight to one with its flag. In this order:

Free

See where you disagree

Look again at each answer where you and your judge disagree, with its decision hidden. Then see what it said, and why. (Details.)

--review
Free

Fix your judge

See what your judge gets wrong, then change its rule with a prompt you copy into an AI assistant, or by hand. (Details.)

--fix
Costs a little, asks first

Try your new judge

Test the new judge on the answers you already marked, side by side with the old one. (Details.)

--try-new-judge

A small local model can grade answers, but it usually can't rewrite a rule well. Use a capable assistant for this step.

You're done when you know what to fix next, or you decide your judge agrees with you often enough for now. After your next eval run, check again.

Details

Everything else, folded away. Open what you need.

What it reads

The results your eval tool already saved in your project folder. It looks for:

  • promptfoo: the results file that promptfoo eval -o or promptfoo export eval writes.
  • DeepEval: the test runs DeepEval saves, in .deepeval/ or the folder DEEPEVAL_RESULTS_FOLDER names.
  • Inspect AI: the logs in logs/.
  • MLflow: the assessments in a local mlruns/ folder or mlflow.db.
  • A table you made: a CSV or JSONL file with an input, an output and a verdict column.
  • Your judge's own results file, after judgekeeper setup: it reads judgekeeper.toml first (below).
  • judgekeeper.record(): the decisions it saved in .judgekeeper/records/ (below).

It names your judge from the results: its name, the first line of its rubric and its model. Several tools or several judges? It asks which one. Too few answers? It says how many there are and prints the command that makes more with your own tool. You run that command, not judgekeeper. Your judge saves its results in a format of its own? See below.

What it never does

  • No AI calls unless you say yes. Then your own judge runs through your own tool; judgekeeper never sees your key, it only checks its name.
  • It never runs your app. Only when you ask your judge again, and say yes, does it run your eval tool, to grade answers it already saved.
  • It never reads your keys. To tell you which key your judge will use, it looks at the names of the variables in .env files, never their values. It never looks outside your project folder.
  • It never reads promptfoo's own database. If promptfoo kept the results there, judgekeeper offers to run promptfoo export for you, which writes them to a file. It asks first.
  • It never changes your .gitignore unless you say yes to judgekeeper setup.

See where you disagree

Free, with no AI call. A disagreement is an answer where your mark and what your judge decided differ.

  1. Look again. You see each disagreement again, mixed with as many answers you and the judge agreed on, and what the judge decided is still hidden. Mark each one Fail, Not sure or Pass.
  2. See what your judge said. For each disagreement you see what your judge decided and its reason, and choose: Your judge was wrong, I was wrong or The rule is unclear, with an optional line of why.

The judge's mistakes go to .judgekeeper/judge-mistakes.csv: the answers to improve your judge's rule with. Unclear cases go to rule-unclear.csv. Your first marks stay the main result.

judgekeeper start --review

Fix your judge

Free, with no AI call, once you have looked at where you disagree. First judgekeeper keeps about a third of your marked answers aside: they test a change fairly later, so they are not shown. From the rest it shows what your judge gets wrong: the answers it passed but you failed, the answers it failed but you passed, your why for each, and words that show up in many of its mistakes.

To change the rule, copy the prompt it gives you into an AI assistant, or write the new rule yourself. judgekeeper never edits your files: it says where the new rule goes. For a judge that gives a score, it also finds the pass mark that fits your marks best, and tests it on the answers kept aside in one click.

Then run your eval once with the new rule, and try your new judge: it tests the change on the answers kept aside.

A small local model can grade answers, but it usually can't rewrite a rule well. Use a capable assistant for this step.

judgekeeper start --fix

Ask your judge again

judgekeeper has your own eval tool grade the answers you marked again, with your own judge. Your app is not run. It works with promptfoo, DeepEval, Inspect AI and MLflow, or with your own judge as a command (--judge-command).

Before any call it shows a plan: your judge, and whether this is exactly your judge, a close copy (and what differs), or a judge it can't ask again (and why); which key your judge will use, by name only; how many judge calls, and a cost range at prices dated in judgekeeper; and what the run touches. Then it asks Go ahead? [y/N]. The answer is No unless you type y.

Then it shows how often your judge changed its decision on the same answer, how well it agrees with you today next to your last result, and how often its new decision matches the one it saved.

judgekeeper start --ask-again

Try your new judge

You fixed your judge's rule or changed its model, and ran your eval once. judgekeeper start notices the new judge and offers to try it on the answers you already marked. You mark nothing new for this.

It rebuilds the new judge from your newest results and has it grade your marked answers, never your new outputs. It shows the same plan and asks the same question as asking again. Then it shows your old judge and your new judge side by side, against the same marks.

A judge changed after you saw its mistakes on these answers will look better on them. So judgekeeper then offers a quick check: you mark 10 Pass and 10 Fail answers from your newest results that you never marked. Its result shows the wide ranges that come with so few answers.

Your main result stays your old judge's. To check the new judge from now on, run judgekeeper start --new: everything moves to .judgekeeper/previous-<date>/, and nothing is deleted.

judgekeeper start --try-new-judge

Running it again

Your marks and results are saved in .judgekeeper/ in your project folder. It holds your answers' text, so commit it only if your data may live in your repository. Run judgekeeper start again and it carries on:

  • You stopped before the end: it asks Continue? and opens the page at the next answer.
  • You have a result: it asks what next: review the answers where you and your judge disagree (free), fix your judge, ask your judge again, Mark more answers, or nothing for now.
  • Your judge changed: when your newest results come from a new version of your judge, it also offers to try the new judge on the answers you already marked.
  • You ran your eval again: it does a re-check. It finds the answers you marked in the new results, says whether your judge changed, and shows the result next to the last one. If your app now writes different answers, your old marks no longer fit, and it offers to mark the new results.
  • You want to start over: judgekeeper start --new moves everything to .judgekeeper/previous-<date>/. Nothing is deleted.

In a script, CI or a coding assistant, it never asks: it prints the flag that answers the question. Marking needs a person. Every flag is in the reference.

Your judge saves results its own way

Many judges are code you wrote, and they save their results in a format of their own. Then judgekeeper start finds nothing it can read. There are three ways in. Pick one.

1. judgekeeper setup: no change to your code

In your project folder, run:

judgekeeper setup

It finds a recent JSON, JSONL or CSV file that seems to hold your judge's results, nested or flat, lists what one line holds, and says how it will read it: what one answer is, the input, the answer, the score or verdict and the reason. It asks only what it cannot tell, for example whether two answers per case (A and B) each count as an answer, and which judge to check. It shows 3 answers as it reads them. Then it asks once before it changes any file: it saves where your results are and how to read them in judgekeeper.toml, adds .judgekeeper/ to .gitignore and judgekeeper to your dev requirements. It never edits your code. Then run judgekeeper start. Your results are somewhere else? judgekeeper setup path/to/results.jsonl.

2. One judgekeeper.record() line

Your judge runs in your own code? Add one line right after it decides on each answer, in your eval code. Then run your eval once, and judgekeeper start finds what it decided.

import judgekeeper
judgekeeper.record(input=question, output=answer, score=0.82, pass_mark=0.5,
                   reason=reason, judge="claude-opus-5", rule=criteria, name="Safe wording")

It never stops your program, uses only Python's standard library, and JUDGEKEEPER_RECORD=0 turns it off. Without the import, or in TypeScript: the reference has a few lines that do the same. judgekeeper never edits your code, but your coding agent can add the line. Paste this prompt: it shows you the change and waits for your yes.

In this project, my LLM judge runs in my own code. Please add the judgekeeper.record() line,
so that judgekeeper can check my judge against my own labels:

1. judgekeeper must be installed in this project's own Python environment, as a dev tool. If
   it is missing, install it there: for example `uv add --dev judgekeeper`, `poetry add
   --group dev judgekeeper`, or `pip install judgekeeper` with the project's virtual
   environment active.
2. Find where this project's LLM judge produces each score or verdict.
3. Right after it, add one call, with the values the judge just used and gave:

       import judgekeeper
       judgekeeper.record(input=..., output=..., score=..., pass_mark=..., reason=...,
                          judge="<the judge's model>", rule=<the judge's rule or criteria>,
                          name="<the judge's or criterion's name>")

   When the judge gives pass or fail, pass verdict=... instead of score and pass_mark. One
   call per judge or criterion. Only in the eval code, never in code that serves real users
   (it saves inputs and outputs to a file); JUDGEKEEPER_RECORD=0 turns it off.
4. Touch nothing else. record() catches its own errors and returns nothing, so it can never
   change what the program does; do not wrap it in code that could.
5. Show me the diff and wait for my yes before saving.
6. Then run the eval once, run `judgekeeper import records .judgekeeper/records --check`, and
   show me what it prints.

3. Your coding agent writes a table

Turn your results into a table: a CSV with the columns id, input, output, verdict (pass or fail) and reason, plus judge_model when you know which model judged. Make one CSV per judge or criterion. Then run:

judgekeeper start your-table.csv

When it reads a table, it prints how many answers it found, how many the judge passed and failed, and the first 3 rows, so a wrong table shows at once.

Your coding agent (Claude Code, Cursor or Codex) can write that table for you. Paste this prompt:

In this project, my LLM judge saves its results in its own format. Please:

1. Install judgekeeper into this project's own Python environment, as a dev tool: for
   example `uv add --dev judgekeeper`, `poetry add --group dev judgekeeper`, or
   `pip install judgekeeper` with the project's virtual environment active.
2. Find where the judge's results are saved, and write a small script that turns them into
   judgekeeper's table: a CSV with the columns id, input, output, verdict and reason, plus
   judge_model when you can tell which model judged. The verdict is pass or fail.
3. Write one CSV per judge or criterion. Leave out rows where the judge gave an error, and
   scores made by a rule instead of an LLM.
4. Keep everything on this computer: never send the data anywhere.
5. Run `judgekeeper start <the CSV file>` and show me what it prints, so I can check the
   counts and the example rows.

judgekeeper start --agent-prompt prints the same prompt in your terminal.

The records format

judgekeeper.record() and the snippets write judgekeeper's own format: one JSON line per decision. It has a version and keeps fields it does not know, so files you write today still read later. judgekeeper import records your-file.jsonl --check checks a file and lists every problem with its line. The fields are in the reference, and the rules as a JSON Schema.

No saved results? Check a judge with a table you make

No saved results, or you would rather work from a spreadsheet? These four steps check a judge with a table you make yourself, using older commands. Advanced commands, step by step runs each one on a small example.

  1. Collect answers from your app

    Save real answers in one file named items.csv. Each row is one answer: an id, the input your app got and the output it wrote. Take ordinary cases and hard ones, good answers and bad ones. Take some that should pass and some that should fail: the more of each, the narrower the result's ranges.

    This step has no command. You make the file in a spreadsheet. From Excel, save it as CSV UTF-8.

    What the file looks like:

    id,input,output
q1,What is the capital of France?,Paris is the capital of France.
q2,What is the capital of Japan?,The capital of Japan is Tokyo.

  2. Mark them

    You read each answer and say pass or fail. That mark is a human label. It is the one part no AI model may do for you: your marks are what the judge is checked against.

    This step has no command either. In the spreadsheet, add a label column and write pass or fail on every row.

  3. Run your judge, or bring what it decided

    judgekeeper needs your judge's pass or fail on the same answers you marked.

    If your tools already saved them, put them next to your marks in one table. Add a verdict column with what the judge said and save the sheet as results.csv. Then run:

    judgekeeper check results.csv --judge verdict --human label

    What you see. This is the result for the small table in Advanced commands:

    Of the answers people passed, the judge passed 100%. Of the answers people failed, the judge failed 33%. It is not trustworthy as a gate.
Not trustworthy as a gate: TPR 1.00, TNR 0.33, kappa 0.41 against human labels.
  - TNR is 0.33 (below 0.80): not trustworthy as a gate.
  - Kappa vs human labels is 0.41 (below 0.6): not trustworthy as a gate.
  - judge identity incomplete: provider, model, snapshot, endpoint, prompt_hash, rubric_version, temperature
  - Too few labels for a rough check (7 labeled pass, 3 labeled fail): it needs 15 of each.
wrote judgekeeper-report/report.json and judgekeeper-report/report.html
    Nothing saved? judgekeeper can run your judge.

    Save your marked answers as anchors.jsonl: one line per answer, such as {"id": "q1", "input": "...", "output": "...", "human_label": "pass"}. The first command runs the judge three times. The first time, it also seals anchors.jsonl, so nobody can change your marks later without it showing. The second compares the judge with your marks and prints the same kind of result.

    judgekeeper judge anchors.jsonl --callable my_judges:judge --runs 3 --out runs/mine
judgekeeper validate anchors.jsonl runs/mine --out reports/mine

    Here my_judges:judge is your own Python function. For other kinds of judge, see Works with what you already use. Advanced commands shows each command with its output.

  4. Read the result

    The first line is the result in plain words, then one of three labels: usable as a gate, usable with care or not trustworthy as a gate. The second line gives the same result as TPR, TNR and kappa (step 5 says what each means). The lines that start with a dash are flags: things to know before you rely on the judge. The last line names the full report. Open it in your browser:

    open judgekeeper-report/report.html

    What you see. One page with the same result, and every answer you and the judge disagree on, with the judge's own reason. On Windows, use start in place of open. On Linux, use xdg-open. See a real report.
